# 查询指南

## 数据源规则

- 优先使用用户明确提供的 DFS 数据库/表，或当前会话表。
- 如果结构不确定，在同一个一次性脚本中使用轻量级 `schema(source).colDefs` 和小样本查询。
- 不要编造数据库、表或列名。
- 如果没有提供数据源，先运行 `ddb_ml/scripts/query_reference.dos` 中的元数据块，再询问用户。
- 元数据发现顺序：
  1. 使用 `getClusterDFSDatabases()` 列出可见 DFS 数据库。
  2. 必要时使用 `getDFSDatabases()` 作为单数据库回退。
  3. 使用 `getClusterDFSTables(false)` 列出可见 DFS 表。
  4. 对单个数据库，使用 `getDFSTablesByDatabase(webDbPath)` 或 `listTables(webDbPath)` 列表。
  5. 对候选表，使用 `existsDatabase`、`existsTable`、`schema(loadTable(...))`、`select count(*)` 和 `select top 20 *` 校验。
- 不要用猜测的 DolphinDB 函数名探测全局元数据。
- 一次全局发现失败不能证明请求领域的数据不存在。应说明失败的查找并请求数据源。
- 只有在一次明确且成功的目录列举覆盖了可用数据库/表，并且列出的 schema 与任务明显无关后，才可以判断“没有相关数据”。
- 对领域任务，根据名称、注释和 schema 给候选表打分。对于设备故障，优先包含 `device`、`equipment`、`machine`、`asset`、`sensor`、`telemetry`、`fault`、`failure`、`alarm`、`error`、`maintenance`、`status` 或 `event` 的名称/列。

## SQL 规则

- 分析时使用只读 `select` 逻辑。
- 分组前把派生桶逻辑放在小型阶段表中。
- 用 `top N` 限制预览。
- 避免打印大表。
- ML 原始建模表需要聚合或 join 时，先过滤，再聚合到建模粒度，最后再 join；不要把多个全量高频明细表直接 join 后再处理。
- 对未来窗口标签，先用查询或聚合脚本物化标签窗口证据，再由 role/raw-data 阶段确认标签列和泄漏排除字段。

## 聊天输出

包含数据源、过滤条件、聚合粒度、行数、重要数值，以及任何缺失的 schema 假设。

## 脚本块选择策略

- 数据源未知时，先选数据库/表发现块，再选 schema、行数和样本块；不要直接猜表名。
- 只知道领域关键词时，先用 schema 字段搜索和按关键词找列块筛选候选表。
- 用户要明细查询时，优先使用等值过滤、时间范围过滤、top N 排序和分页/采样块，保证输出有界。
- 用户要统计时，优先使用分组聚合或多指标聚合块；复杂时间桶先做小型阶段表。
- 涉及 join 时，先做左右表行数、join key 空值、重复度检查，再做 join 后行数变化检查。
- 每次查询后使用结果摘要块，把数据源、过滤条件、输出行数和限制条件整理到聊天答案中。
- 已知数据库但目标表不确定时，使用整库候选表画像块；报告候选表行数、列数、分区列和排序列后再选择表。
- 报告或建模需要周期基础表时，使用月度聚合和月度 lag 块；仅在时间列和值列都已确认后使用。
- SQL 摘要块只用于聊天解释，不替代 schema 校验和有界查询执行。

## ML 原始数据阶段补充

- 清洗前若需要构建建模输入表，先读取 `raw-data-selection-guide.md`，再从 `query_reference.dos` 选择块 11-16、21-23。
- 聚合标签或派生目标列时，输出应说明观测窗口、标签窗口、聚合粒度和标签来源字段。
- join 前必须用块 14 检查 key 空值、重复度和 join 后行数变化；join 后再进入 role 模块复核标签、实体、时间和候选特征。
- 如果 SQL 连续失败，不要扩大复杂 SQL；拆成更小的阶段表，并在聊天中说明已验证的中间口径。
