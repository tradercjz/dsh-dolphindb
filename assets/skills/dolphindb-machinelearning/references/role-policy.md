# 角色策略

## 优先级

1. 用户明确指定的列。
2. 当前 schema 以及可用注释。
3. 保守的类型/名称启发式规则。

## 启发式规则

- 时间列：时间类型，或名称包含 `time`、`date`、`ts`、`timestamp`、`start`、`end`、`create`、`update`。
- 实体列：标识符类字段，例如 `id`、`device`、`equipment`、`machine`、`asset`、`customer`、`order`、`product`、`line`、`factory`，并且基数为低到中等。
- 标签列：显式目标列，或名称包含 `label`、`target`、`status`、`fault`、`failure`、`fail`、`alarm`、`error`、`down`、`maintenance`、`class`、`result`。
- 特征列：排除标签、实体、原始时间和明显质量/状态文本后的数值列。
- 数值列：适合聚合的数值指标列。

## 领域匹配

角色推断前，先检查候选表是否符合用户的领域意图。对于设备故障预测，schema 应包含类似设备的实体、时间/事件列，以及至少一个故障/状态/事件信号或遥测特征。销售订单、客户、产品或财务表与该任务无关，除非用户明确说明其中包含设备标签。

如果只看到无关表，报告可见表并请求正确数据源。不要把一次不完整的目录查找说成已经完整证明不存在设备数据。

## 未来窗口标签

对于“未来 N 天/周”的分类任务，将标签定义为每个实体是否在 `(as_of_time, as_of_time + horizon]` 内发生故障事件/状态。必需角色是实体列、预测时点列和故障事件/状态定义。只能使用 `as_of_time` 及之前已知的特征。

如果用户目标包含“未来”“接下来”“后续”“下一天”“未来 24 小时”等语义，角色结论必须明确区分：

- 观测时间列或观测日。
- 标签窗口开始和结束。
- 标签来源字段或事件定义。
- 最终标签列。
- 不能进入特征的标签组成字段。

未来窗口标签应在原始建模数据阶段完成物化和确认，不能默认交给特征工程阶段再位移或重建。

## 停止条件

对于监督学习，当标签不明确且存在多个合理标签时，停止并询问用户。

对于未来窗口预测，如果无法推断故障事件/状态定义，或无法推断实体列/时间列，也必须停止。

## 脚本块选择策略

- schema 已确认后，先使用角色候选评分块，输出候选列、命中规则、类型和名称特征。
- 需要实体级分析时，使用实体列基数检查块，避免把高基数流水号误当作业务实体。
- 涉及时序、窗口预测或报告任务时，使用时间列 min/max 检查块确认时间范围和可用粒度。
- 监督学习任务必须使用标签分布和标签适配检查块；类别过少、单一标签或缺失严重时停止说明。
- 未来窗口预测必须使用未来窗口必要条件检查块，确认实体列、预测时点和事件/状态定义都存在。
- 交给下游阶段前，使用角色结论摘要表块，把实体、时间、标签、特征候选和风险统一输出。
- 工业数据任务还要使用工业语义角色候选块，识别质量、单位、状态、开始/结束时间、持续时间、更新时间、入库时间、点位、报警码、维修类型、工单、批次和工艺列。
- source mode 摘要用于选择下游策略：`timeseries_sensor` 可启用时间间隔和信号异常检查，`equipment_status` 可启用状态区间检查，`production_record` 和 `quality_record` 优先审查业务 key、质量和批次/工艺字段。
- 工业角色有多个合理候选时，先输出角色确认清单并请求用户确认，不要直接进入清洗或建模。

## 与原始数据选择的衔接

- 角色模块只负责识别和解释字段职责；如果需要用 SQL 派生未来标签、聚合输入表或 join 多表，回到 `query_reference.dos` 的过滤/聚合/join 块完成物化。
- 角色模块输出给下游时，应包含实体列、时间列、标签列、候选特征、泄漏排除和待用户确认项。
- 当 schema 中已有完整列摘要时，不要因为没有固定模板字段就声称 schema 不足；应基于可见列给出保守角色判断或明确列出需要用户确认的业务口径。
