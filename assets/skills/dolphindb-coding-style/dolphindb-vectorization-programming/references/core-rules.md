# 向量化规则总册

## 编码前固定判断顺序

在进入具体实现前，请按以下顺序逐项确认。如果前四步尚未明确，不要提前选择 `JIT`、`peach` 或复杂的桥接方案。

1. **确定处理对象**：向量、矩阵、表、数组向量、两张表之间的关系，还是流数据批次。
2. **确定输出形式**：单个值、与输入等长的序列、每组一条结果、窗口级结果、宽表结果，还是实时增量输出。
3. **确定结果依赖**：仅依赖当前位置的值，依赖前一位置或累积状态，依赖匹配对象，依赖窗口范围，依赖分组，还是依赖表级查询。
4. **确定逻辑应放置的承载层**：普通批量表达式、表查询（SQL）、分组上下文、窗口函数、流引擎，还是独立的计算核。
5. **最后才判断是否需要执行层升级**：`JIT` 编译、并行（`peach`）或分布式执行。

---

## 第一组：明确任务定义

### 规则 01：先用“对象、依赖、输出”描述任务，再编写表达式

代码复杂化的常见根源不是函数使用不当，而是任务本身未被清晰定义。仅说“把循环改成向量化”不够，至少需要说明：处理哪类对象，结果依赖哪些数据，输出保持什么形态。

该规则旨在将关注点从“代码的表面形式”拉回到“计算的本质”。一旦这三项明确，许多技术路线自然收敛。例如：

- 结果仅依赖当前位置，通常不会引入迭代状态。
- 输出需与输入等长，就不应使用 `group by` 聚合后再回填。
- 数据已在表中，就不宜先提取到脚本层再逐段循环。

在进入后续规则前，至少应能回答：
- 处理对象是向量、表、矩阵、数组向量，还是表间关系。
- 输出是单个标量、一列值、一张与原表等长的结果表、一张分组汇总表，还是一个流式输出批次。
- 结果依赖的是当前位置、前一状态、滑动窗口、所属分组，还是匹配到的另一对象。

### 规则 02：输出形式比函数名称更能决定技术路线

同一业务含义，因输出形式不同，实现路径可能完全不同。只关注最终状态与保留过程状态不可共用同一路线；每组一条结果与组内等长结果也不应使用相同的分组入口。

编写前先将输出形式固定下来，函数选择会稳定得多。常见区分：

- 单个最终结果：优先使用归约路线（如 `sum`、`max`）。
- 与输入等长结果：优先使用逐列运算、窗口函数、`context by` 或批量回写。
- 每组一条结果：优先使用聚合分组。
- 累计序列输出：优先使用累计分组或状态序列函数。
- 宽表/面板结果：优先考虑矩阵运算、数组向量或透视（pivot）。

如果输出形式仍模糊，继续堆砌函数意义不大。

## 第二组：将数据置于正确结构

### 规则 03：数据结构应先服务于计算，再服务于书写便利

向量化代码的上游判断，首先是数据应放在何种结构之中。结构选错，即便没有显式循环，也会被迫编写大量中间转换代码。

按以下顺序做初步判断：

- 一维同类型数值：优先使用强类型向量。
- 等长二维数值：优先使用矩阵。
- 结构化记录：优先使用表。
- 同构的多档字段：优先使用数组向量或等效批量结构。
- 字典和元组：优先用于封装、组织和映射，不宜作为高频数值计算的核心路径。

该规则并非要求所有数据只有一种结构，而是要求核心计算发生在适合的结构上。结构错误的常见后果不是运行报错，而是本可直接书写的批量表达式被拆解为众多过渡步骤。

### 规则 04：计算的维度必须与对象形态对齐

数据结构放置正确后，需确认函数在哪个维度上整体作用。许多代码的问题不在于“有无循环”，而在于对表施加了行级语义而实际应为列级运算，或对矩阵使用了默认维度而实际应按另一维度计算。

重点检查四项：

- 计算发生于元素级、列级、行级、组级还是窗口级。
- 结果长度保持不变、缩减为标量、还是按组或按窗口输出。
- 函数的默认维度是否与当前对象匹配。
- 取子集、切片、排序后，结果形态是否发生变化。

维度判断错误时，代码也许能执行，但语义已经偏离。

### 规则 05：结构转换是正常的设计步骤，而非弥补手段

`matrix`、`flatten`、`values`、`flip`、`transpose` 等结构转换，不是为了勉强让代码运行，而是为了将计算转移到更合适的对象上。

判断是否应该转换的两项标准：

1. 转换后能否直接进入更自然的批量处理入口。
2. 转换后能否显著减少拆列、拼列、逐项回填和中间桥接对象。

若两项均成立，转换就是正路。反之，若频繁在多种结构间来回搬运数据，通常说明前期的结构判断还未完成。

## 第三组：优先采用批量原语

### 规则 06：可构成稳定批量流水线时，不使用脚本控制流

当处理流程可自然分解为“清洗→过滤→排序→累计→聚合→转换”等批量步骤时，应优先写成连续的批量流水线。其优势并非代码更短，而是每步语义清晰，输入、输出与中间状态一目了然。

该规则的前提是：
- 每步都是真正的批量操作。
- 步骤间先后关系明确。
- 中间步骤没有额外副作用。

若每步都能在整列、整表或完整窗口上稳定完成，继续退回到 `for`、`if`、临时数组和逐项收集，通常只会让语义更模糊。

### 规则 07：先寻找专用内置函数，再考虑高阶函数与自定义组合

在 DolphinDB 中，大量低效代码的对应功能已有现成内置入口，无需从通用高阶函数或脚本模板开始。经验上，按以下顺序选择：

1. 优先确认是否存在专用内置函数或固定的惯用写法。
2. 若专用入口不覆盖，再考虑高阶函数或函数组合。
3. 若仍无法承接，再考虑显式递推核与执行层升级。

原因在于，专用内置函数通常已对数据结构、默认维度、边界情况和性能细节做了充分处理。过早使用过于泛化的模板，常使原本直接可写的任务不必要地复杂化。

### 规则 08：仅依赖当前位置的条件逻辑，默认使用批量条件表达式

当每个位置的结果仅取决于当前值或当前行的一组固定规则时，应首先将其理解为批量条件表达式，而非循环控制流。

满足本条规则时，优先检查：
- 条件赋值（如 `iif`）
- 布尔过滤
- 布尔回写
- 基于规则表或规则字典的批量判断

一个实用的判断依据：检查循环体内是否真正依赖 `i-1`、累积状态或其他位置的值。若不依赖，保留逐项的 `if/else` 通常并非更稳妥的选择，而是未能将问题还原为其本来的批量语义。

### 规则 09：依赖前值、累积值或分段状态时，先归类为特定序列问题

序列问题最容易被笼统地写成“有状态的循环”，但其内部至少包含四类不同路线：

- 标准累积：到当前位置为止的和、最大值、计数等。
- 相邻关系：与前值的比较、差值、方向变化、连续段识别。
- 分段状态：达到阈值后重置、按事件断段、按累积量换段。
- 递推输出：仅需最终状态，或需保留每一步的状态。

只有先区分这四类，才能决定是采用 `cum*`、`prev/next/deltas`、分段原语、`reduce` 还是 `accumulate`。该规则的重点不是“禁止写循环”，而是确认当前循环正在模拟哪一类序列原语。

### 规则 10：核心动作为“查找对应项”时，将问题重定义为匹配或对齐

某些任务的主要开销不在算术运算，而在于“定位应使用的数据项”。一旦识别出这种特征，就不应继续以普通逐元素计算的方式来处理。

常见信号：
- 对同一目标对象重复扫描。
- 先维护标签到位置的映射，再据此取数。
- 左侧每一行都需到右侧对象中查找最近记录或时间范围内的记录。
- 多档位或异构对象之间反复手工对齐。

命中此规则时，后续路线通常会转到查找、对齐、时间关联或窗口连接，而非普通的条件表达式。先明确“如何找到对应项”，改写方向才会明确。

### 规则 11：同一逻辑作用于整列、整表或一批同类对象时，使用统一入口

如果仅仅“当前对象”在变化，而处理逻辑始终不变，就不应再手工遍历列名、逐列赋值或逐个对象收集结果。

该规则覆盖三类高频场景：
- 整表的行间关系变化（如重排序、截取、统一筛选）。
- 同一种列变换作用于多个列。
- 同一函数作用于一批结构相同的对象。

需要先区分“整表关系”“列级统一变换”和“多对象统一映射”分别属于哪一类，再选择合适入口。真正的问题往往不在于循环本身，而在于没有把“同一逻辑作用于一组对象”这一意图表达清楚。

### 规则 12：数据清洗、修复和类型转换，默认按整列处理

当任务已明确为数据修复而非业务计算时，优先级应切换。此时更重要的是一致性、可复用性和整列语义，而非逐项处理每个异常点。

命中此规则时，优先确认：
- 该操作属于空值处理、重复值处理、异常值处理还是类型恢复。
- 修复结果是整列替换、整列过滤，还是产生新的清洗列。
- 清洗动作能否在整列或整表层面一次性完成。

一旦任务被定性为“修复数据”，继续围绕逐值解析和逐值回写组织脚本，通常会破坏本可保持一致的整列操作。

### 规则 13：窗口问题需先定义窗口，再选择函数

窗口类代码容易表面相似，但固定计数窗口、时间长度窗口、时间分桶、会话窗口、事件段窗口和累积量窗口并非同一概念。先阐明窗口定义，比先记忆函数名称更重要。

进入函数选择前，至少应确认：
- 窗口的计量方式：记录条数、自然时间、交易日历、事件断点还是累积量。
- 输出长度：每窗口一条结果、与输入等长，还是仅保留部分窗口的结果。
- 窗口初期结果的处理方式。
- 空值、空桶和不规整时间戳的处理策略。

这些信息不明确时，很容易在专用窗口函数与通用窗口函数之间做出错误选择。

### 规则 14：分组问题需先说明每组的输出形式

“分组”并不自动等同于 `group by`。技术路线的首要决定因素是“每组最终需要产生什么”：

- 每组仅需一条结果：走聚合路线。
- 组内每一行都需保留结果：走等长分组路线（如 `context by`）。
- 每组结果需沿时间或顺序累计展开：走累计分组路线。
- 结果需转换为宽表或面板：走透视路线。

许多低效代码的问题不是不会分组，而是先将每组合并为摘要行，然后又试图将摘要补回明细。只要一开始就明确每组输出形式，后续入口就不会偏移。

## 第四组：决定逻辑的承载层

### 规则 15：数据已在表中时，优先让 SQL 在表内完成工作

当数据已位于表中，应优先将过滤、分组、时间关联、结果整形和查询组织保留在 SQL 路径中。过早将列、子表或中间结果提取到脚本层，通常会带来额外成本：重复扫描、重新分组或重新对齐，以及在查询内本可完成的结果整形被拆分到外层。

该规则还要求单独检查查询组织，而不仅看函数名是否正确。尤其注意：
- `context by`、`csort`、`limit`、`order by` 的先后关系。
- 分布式场景下是否命中分区剪枝。
- 是否存在不必要的中间表和多次扫描。

函数选对不等于查询组织就合理。

### 规则 16：数据已进入流处理时，优先按批次和引擎组织

流处理场景的第一判断不是“如何将逐条逻辑塞进回调”，而是“当前输入属于批次、实时状态、窗口指标、双流匹配还是历史回放”。一旦数据按批次到达，就应优先按批次表处理，而非将其重新拆回逐条脚本。

该规则要求先确认三类语义：
- 输出语义：每个批次产生什么结果。
- 时间语义：事件时间、处理时间和窗口时间分别是何种含义。
- 匹配语义：是否涉及多流关联、历史近邻、时间范围或状态缓存。

在此基础上，再判断是采用普通批次表达式、内置增量算子、流引擎流水线还是历史回放。能用引擎承接的状态和窗口，不应首先写成回调中的缓存表和手工回溯扫描。

## 第五组：最后考虑执行层升级

### 规则 17：表达路线稳定后，再引入 `JIT`、并行和分布式

执行层升级会放大收益，也会放大错误。当数据结构、计算维度、窗口语义、分组输出或 SQL 组织尚未理清时，直接采用 `JIT`、`peach` 或分布式方案，往往只是在加速运行一条尚未理顺的路线。

进入执行层前，至少需确认：
- 处理对象和输出形式已稳定。
- 主要原语和承载层已选定。
- 主要瓶颈确实在于解释开销、单线程吞吐或集群执行方式。

在这些前提未满足时，执行层升级通常不是性价比最高的下一步。

### 规则 18：`JIT` 仅负责难以拆解的热点计算核，不接管整体业务流程

`JIT` 的定位应很明确：它是向量化路线之后的增强手段，而非默认首选或通用加速开关。

适合考虑 `JIT` 的情况：
- 单步状态强依赖前一步结果，短期内无法改写为稳定的批量原语。
- 计算核内部数值计算密度高。
- 同一热点函数被反复调用，解释开销显著。

不适合优先使用 `JIT` 的情况：
- 仅仅对现有内置函数进行简单包装。
- 主要问题仍在于表级组织、分组路线、窗口语义或 SQL 组织。
- 计算核本身很短，但外部调用极为频繁，导致切换开销不划算。

实际使用时，还需单独检查类型稳定性、签名稳定性及支持范围。分组组织、流订阅、引擎连接和结果写出等环节通常应继续留在 `JIT` 外层。

---

## 规则判断的结束条件

当满足以下三点时，可以认为规则层的判断已足够，可进入后续阶段：

1. 已能清晰描述处理对象、输出形式、结果依赖关系和承载层。
2. 已明确应优先查看哪类批量原语。
3. 如果任务是审查已有代码，已能判断其最可能命中的异常类型。

满足之后：
- 从零开始编写，可直接进入实现。
- 审查或改写已有代码，可进一步参阅反模式文档（`anti-patterns/`）进行异常识别与路由。
