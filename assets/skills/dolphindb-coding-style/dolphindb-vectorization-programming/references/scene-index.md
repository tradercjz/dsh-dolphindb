# 参考场景索引：向量化反模式与优化路径

本索引包含了所有已知的低效代码模式 (`tag`) 及其所属场景 (`scene`)。它的作用是，在拿到一段待优化的代码时，帮助你**快速锁定它命中了哪种典型问题**，并找到对应的详细解法和改写案例。

## 如何使用本索引

当你面对一段已有的 DolphinDB 代码时，按以下三步进行：

1.  **观察计算特征**：代码处理的**对象**是向量、表还是流数据？它期望的**输出**是与输入等长、每组一条，还是一个值？
2.  **识别违和感（代码异味）**：检查是否存在显式 `for/while` 循环、频繁的切片 (`x[i:j]`)、大量 `append!`、手工维护的 `state/tmp` 变量、`distinct` 后接循环处理、`group by` 后又 `join` 回原表等行为。
3.  **按图索骥**：在下方索引中，寻找与上述“异常”最匹配的 `快速识别特征` 和 `常见外观`，进入对应的场景文档 (`scene-XX-*.md`)。

## scene-01 数据承载结构选择不当

**核心问题**：数值计算任务对数据结构的“形状”或“类型”有特定要求，但代码当前使用的主对象结构不匹配，导致后续计算走了弯路。

### `S01-T01`：一维数值向量滞留在元组或泛型结构中
- **快速识别**：代码生成数据用 `[]` 然后 `append!`；或者把多个向量放进元组后直接计算。后续运算为典型的数值四则运算或统计。
- **判定**：当数据本质是等长、同类型的一维序列，但载体不是 `FAST VECTOR` 时命中。

### `S01-T02`：等长二维数据未使用矩阵承载
- **快速识别**：数据逻辑是二维的（行×列），但承载形式是窄表或脚本层的嵌套列表。后续计算集中在行列切片、行列统计或矩阵运算上。
- **判定**：当计算逻辑已经是在对等长二维数值做操作，而对象不是 `matrix` 时命中。

### `S01-T03`：同构多档字段仍分散存储为平行列
- **快速识别**：列名有明显数字后缀（如 `px1, px2...`、`vol1, vol2...`），或者多个列结构完全一致。操作需要对这一“组”列做统一变换。
- **判定**：当同一实体的同质属性被拆成多列，导致批处理需要手工遍历列名时命中。

### `S01-T04`：纯数值表未切换至矩阵进行数值计算
- **快速识别**：对一张只含数值列的表，频繁使用 `byRow`、行级函数或行号索引去做按行统计或向量乘法。
- **判定**：当表的强结构化语义（列名、索引）完全未被使用，计算本质是纯数值的二维运算，却未转成 `matrix` 时命中。

### `S01-T05`：向量化函数直接套用于复杂对象
- **快速识别**：定义了一个入参为向量的函数，但在调用时直接将表或矩阵传入，导致报错或结果不符预期后，又回退到手动拆列循环。
- **判定**：当函数的“输入假设”与“实际输入对象”不匹配时命中。

### `S01-T06`：计算前未执行必要的结构转换
- **快速识别**：核心计算逻辑明显，但代码中途反复出现手工取列、拼列、拆解再组装的动作，而不是一次性将数据转到最顺手的形式再计算。
- **判定**：当代码的复杂度主要来自“在原结构上硬算”而非“计算本身”时命中。

## scene-02 批量条件判断仍用逐元素控制流

**核心问题**：每个输出位置的结果仅取决于当前行的值或固定的外部规则，但代码使用了 `for/if` 而不是向量化的条件表达式。

### `S02-T01`：逐元素执行`if/else` 自判断
- **快速识别**：循环体只访问 `x[i]` 等当前位置，进行条件判断并赋值/过滤。
- **判定**：当循环索引 `i` 的结果与 `i-1` 无关，纯属当前元素的条件映射时命中。

### `S02-T02`：按外部规则表进行逐元素查表判断
- **快速识别**：循环体内根据当前行的某个键值（如 `sym`），去一个字典或规则表中查找阈值或映射规则，再做判断。
- **判定**：当映射逻辑完全可以由向量化查找（如 `dict[key_vector]`）或 `iif` 一步完成，却写成循环时命中。

## scene-03 序列依赖关系仍用手工状态维护

**核心问题**：结果依赖前项、历史累计或分段状态，代码手工维护着 `state`、`prevVal` 等变量，而不是使用序列专用函数。

### `S03-T01`：手工维护跨步长的累计状态
- **快速识别**：循环外定义 `cumSum` 或 `cumMax` 等变量，循环内逐步更新并写入结果数组。
- **判定**：当手工逻辑等价于 `cumsum`、`cummax`、`cumprod` 等标准累计函数时命中。

### `S03-T02`：手工比较和传播相邻元素关系
- **快速识别**：代码大量使用 `x[i]` 与 `x[i-1]` 比较，或手动将前一结果向后复制传递。
- **判定**：当逻辑等价于 `prev`、`next`、`deltas` 或 `ffill` 时命中。

### `S03-T03`：手工管理分段触发与段内累计
- **快速识别**：循环内存在 `if (cond) reset` 类逻辑，同时维护段编号和段内累计变量。
- **判定**：当需要在条件触发时重置累计，却又不是直接用分段原语时命中。

### `S03-T04`：手工展开递推迭代或终值归约
- **快速识别**：循环结束只取最后状态，或循环体仅仅是将一个固定规则反复作用于状态变量。
- **判定**：当逻辑等价于 `reduce` 或 `accumulate`，却由手工循环实现时命中。

## scene-04 匹配与对齐操作仍依赖手工扫描

**核心问题**：主要计算成本花在“找到对应项”上，代码在左侧每一条记录上对右侧对象进行扫描或 `find`，而非使用对齐/窗口连接。

### `S04-T01`：反复扫描目标对象以定位命中项
- **快速识别**：对左侧每一条，在右侧向量中从头搜索第一个/最后一个满足条件的值或位置。
- **判定**：当存在“左侧逐条 -> 右侧全量扫描”的模式时命中。

### `S04-T02`：将标签映射为下标后再取数
- **快速识别**：先维护一个标签列表，然后用 `find` 得到下标，再用下标去切片或索引矩阵/表。
- **判定**：当对象本身支持标签直接访问，却多此一举先转数字下标时命中。

### `S04-T03`：手工对齐结构相近的两批数据
- **快速识别**：左右两批数据维度相似，代码却为每一行或每一组建立临时映射来取对应值做差值或比较。
- **判定**：当两批数据的配对逻辑可通过对齐功能一步完成，却写了手工配对时命中。

### `S04-T04`：逐条记录去另一表查找时间对应关系
- **快速识别**：左侧逐条，右侧按时间回扫找最近的前一条/后一条记录，或时间窗口内记录。
- **判定**：当“时间邻近匹配”或“窗口关联”逻辑被手工实现时命中。

## scene-05 对一批同类对象的统一操作被拆散

**核心问题**：同一个处理逻辑要施加到多个对象（列、表、向量）上，代码用 `for` 循环遍历对象列表逐一处理，而非使用高阶函数或整表操作。

### `S05-T01`：整表级的统一行操作被拆成逐列循环
- **快速识别**：为改变整张表的行序或截取子集，去循环遍历所有列名，对每列做同样操作。
- **判定**：当操作目标是“整表”，却被拆解为“列级操作”时命中。

### `S05-T02`：同一种列变换逐列手工重复调用
- **快速识别**：`for(col in t.colNames()) { t[col] = func(t[col]) }` 或类似模式。
- **判定**：当“同一函数作用于一列或多列”的逻辑，未使用 `each` 或 SQL 批量列操作时命中。

### `S05-T03`：一批同构对象逐一施加同一种函数
- **快速识别**：把多个结构一样的对象放进列表，然后 `for` 循环对其逐一执行同一个函数，收集结果。
- **判定**：当代码唯一变化的只是“当前对象是谁”，却展开了循环时命中。

## scene-06 整列清洗与类型转换被逐值处理

**核心问题**：任务已明确是数据修复、类型标准化或质量筛选，应该整列应用，但代码仍围绕单个值进行解析和回写。

### `S06-T01`：统计概览被拆成多次独立计算
- **快速识别**：为获得数据集的 `min, max, avg, std`，分别写了多条独立的语句，导致数据被多次扫描。
- **判定**：当只求一个概览统计，却未用 `summary` 或一次 SQL 聚合完成时命中。

### `S06-T02`：事后逐步扫描来处理重复值/空值/异常值
- **快速识别**：循环内逐行判断 `isNull`、`isDup`，然后构造标记数组，再根据标记去过滤或替换。
- **判定**：当整列清洗被分解为“逐行判断+逐行操作”时命中。

### `S06-T03`：类型转换/格式修复逐值解析
- **快速识别**：循环内对字符串列调用 `datetimeParse`、`int` 或 `trim` 等纯函数，再写回。
- **判定**：当整列的类型转换或清洗函数可以被向量化调用，却被拆成逐值调用时命中。

## scene-07 窗口与分桶计算仍手工切片

**核心问题**：需要在序列或时间序列上滚动窗口或时间分桶，代码自己计算窗口的起点终点并切片聚合，而不是用滑动窗口/分桶函数。

### `S07-T01`：手工计算并切片固定计数滑动窗口
- **快速识别**：代码通过控制 `i` 和 `i+window-1` 的边界，反复对向量进行 `[i:j]` 切片并聚合。
- **判定**：当窗口大小固定为条数，逻辑等价于 `moving` 或 `rolling` 系列函数时命中。

### `S07-T02`：手工计算时间分桶与填补缺失桶
- **快速识别**：先手工生成时间戳序列作为桶边界，再循环判断每条记录落在哪个桶，最后还要手动补上缺失的时间桶。
- **判定**：当逻辑等价于 `timeBucket` 或 `resample` 时命中。

### `S07-T03`：手工维护基于时间/会话/累计量的动态窗口
- **快速识别**：循环内需要比较当前记录与前一记录的时间差，或累计成交量来判定窗口是否结束并触发计算。
- **判定**：当窗口边界由逻辑条件动态决定（如时间范围窗口、成交量切片），却手工管理窗口状态时命中。

## scene-08 分组计算被错误地展开或回填

**核心问题**：需要得到与原始明细表等长的分组结果，或需要组内排序、组内累计，但代码先用 `group by` 压扁再回填，或在分组外手工循环处理。

### `S08-T01`：分组结果本应保持等长，却先聚合再回填
- **快速识别**：先 `select ... group by` 得到每行一条的统计，再 `lj` 或手动循环将统计值填回明细表的每一行。
- **判定**：当分组计算的最终诉求是“在原表上增加一列组统计值”，却走了“聚合-连接”路线时命中。

### `S08-T02`：组内排序/截取被拆成逐组循环
- **快速识别**：先得到分组键列表，然后 `for` 循环筛选每个组的数据，再独立排序和 `top` 截取。
- **判定**：当 SQL 的 `context by` 配合 `limit` 或组内窗口可以一步完成，却拆成循环时命中。

### `S08-T03`：分组累计/递推被放到组外展开
- **快速识别**：在每个组的循环内部，维护一个累计变量或递推逻辑，手动生成组内结果序列。
- **判定**：当需要使用组内累计（`cumsum` + `context by`）或分组递推，却用了手动状态管理时命中。

## scene-09 查询与结果整形过度依赖脚本层

**核心问题**：数据本身已经在表中，但过滤、聚合、时间关联或长宽转换的后续步骤被拉到 SQL 外部由脚本循环完成。

### `S09-T01`：将表取至脚本层再进行本可内嵌的聚合
- **快速识别**：先用 `exec distinct key` 把键值取出来，再在脚本层用键值轮询原表，或者把列拉出来在脚本层 `sum`。
- **判定**：当脚本层在做 SQL 本可以完成的第二层聚合或关联时命中。

### `S09-T02`：查询结果的打包与整形在 SQL 外手工完成
- **快速识别**：SQL 查出了明细数据，然后在脚本层用 `for` 循环把它转成宽表、数组向量或矩阵。
- **判定**：当最终结果形态可由 `pivot by` 或转换函数直接完成，却留在脚本层手工处理时命中。

### `S09-T03`：时间逻辑导致多次扫描和中间表
- **快速识别**：为了添加一个时间分桶标记或滑窗计算，先查一次落中间表，再基于中间表查一次。
- **判定**：当一条 SQL 配合 `context by` 窗口可以完成，却被拆成多步扫描时命中。

## scene-10 流处理中手工管理状态与批次

**核心问题**：数据已进入流处理模式，但实时状态、窗口、多流关联或历史回放逻辑仍手写在回调函数中，而不是使用引擎或内置状态算子。

### `S10-T01`：流数据批次被拆成逐条消息循环
- **快速识别**：流订阅设置了 `msgAsTable=true`，但在回调 handler 里，还是用 `for` 循环遍历传进来的这张批次表。
- **判定**：当流批次处理退化为逐行处理时命中。

### `S10-T02`：手工维护实时窗口与多流关联缓存
- **快速识别**：回调函数里声明并维护了大量字典或临时表，用来存不同 key 的最新状态、窗口数据，或为双流关联做缓存。
- **判定**：当内置的时间窗口引擎或键值状态引擎可以直接承载这些状态时命中。

### `S10-T03`：多阶段流计算靠重复订阅和中间流表串接
- **快速识别**：为完成 A->B->C 的数据加工，建了多个订阅，每一步输出都写入一个新的流数据表供下游消费。
- **判定**：当可以用流计算引擎的级联（流水线）直接串联，却用了多级订阅和实体中间表时命中。

### `S10-T04`：历史回放与实时链路使用两套处理逻辑
- **快速识别**：实时链路是一套代码，历史数据回测时，却用 `for` 循环模拟逐条输入，或用完全不同的批处理脚本计算。
- **判定**：当需要保证“流批一体”却维护了两套不同的计算逻辑时命中。

## scene-11 执行层升级时机不当或方式笨重

**核心问题**：逻辑路线上已无大问题，瓶颈在解释执行或单线程吞吐，但 JIT、并行或分布式的引入要么过早，要么实现方式粗糙。

### `S11-T01`：递推核已固化，仍忍受解释执行开销
- **快速识别**：一个逻辑清晰、不再变动的 `for` 循环或组内自定义函数，占据了主要耗时，但未尝试 JIT 编译。
- **判定**：当代码执行慢，且热点集中在纯数值、高密度的自定义循环核上时命中。

### `S11-T02`：明确的终值递推或全路径映射仍用手工循环
- **快速识别**：问题形态完美契合 `reduce`（只要终值）或 `accumulate`（保留全路径），但代码还是写了完整循环。
- **判定**：当循环的目的纯粹是为了传递状态，且单步规则稳定时命中。

### `S11-T03`：可并行的独立重任务仍串行执行
- **快速识别**：循环内每次迭代的计算量巨大且完全独立，但代码还是单线程顺序跑，导致执行时间线性增长。
- **判定**：当任务具有“高度数据并行”特征，却未用 `peach` 或分布式方案时命中。
