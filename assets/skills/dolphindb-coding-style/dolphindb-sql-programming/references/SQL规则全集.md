本文件提供 DolphinDB SQL 编程规则的完整版本。`SKILL.md` 保留压缩后的主体规则；需要更完整的规则说明时，阅读本文件。

## 一、设计阶段规则

### 规则 01：数据已在表中时，优先判断任务是否应留在 SQL 内

过滤、投影、分组、关联、窗口、透视、更新、删除和结果整形都可以由 DolphinDB SQL 直接表达。过早把列向量、子表或中间结果取回脚本层，会增加扫描、合并和再分组成本。

### 规则 02：先明确 SQL 输出形态，再选择入口

每组一行使用 `group by`；明细等长输出使用 `context by`；累计分组输出使用 `cgroup by`；二维重排使用 `pivot by`；窗口连接使用 `wj` 或 `pwj`；最近历史匹配使用 `aj`。不要只凭“需要分组”或“需要关联”选择语法。

### 规则 03：SQL 与 DolphinScript 可以混合使用

DolphinDB SQL 可以直接引用脚本变量、表对象、自定义函数和内置函数。SQL 可作为变量值、函数返回值或函数参数。需要访问分布式表时，若未使用 catalog，应先通过 `loadTable` 等函数获得表对象。

### 规则 04：标准 SQL 写法可用，但写入和访问方式需要区分场景

DolphinDB 支持标准 SQL 风格的 `create table`、`insert into`、`select`，也支持通过 SQL 创建分布式库表。分布式表写入虽支持 `insert into`，但一般性能不如 `append!` 或 `tableInsert`。启用 catalog 后可使用 `catalog.schema.table` 形式访问分布式表。

### 规则 05：时间语义必须在编码前确定

涉及时间关联、时间分桶、时间窗口和交易日历时，应明确时间列类型、窗口方向、窗口单位、是否补齐空桶、是否使用交易日历，以及窗口结果是否与左表等长。`DATETIME` 场景中 `0:4` 不等于 4 分钟，应写成 `0m:4m`。

### 规则 06：组内顺序是 SQL 语义的一部分

使用前值、差分、累计、滑窗、`limit`、`first`、`last` 等顺序相关逻辑时，应明确组内顺序来源。需要排序时使用 `context by ... csort ...`，不要依赖未说明的原始顺序。

### 规则 07：动态字段需求应先判断复杂度

动态列名、动态过滤条件、大量相似字段、批量相似查询适合 SQL 元编程。固定 SQL 不应改成元编程；简单动态列名可用宏变量或字段序列，复杂表达式再使用 `sql`、`sqlCol`、`makeCall`、`expr` 等结构化函数。

## 二、过滤、关联与分区规则

### 规则 08：能用键集合过滤时，不应先做表连接

如果另一张表只用于提供筛选键，优先 `exec key from dim where ...` 得到键向量，再在主表中使用 `where key in keys`。`join` 更适合补充右表字段或构造宽结果；仅用于过滤时通常成本过高。

### 规则 09：时间近邻匹配优先使用 `aj`

左表每条记录需要匹配右表中相同键下同一时刻或之前最近记录时，应使用 `aj`。典型任务包括交易匹配最近报价、状态表补最近历史值。

### 规则 10：时间范围匹配并聚合优先使用 `wj` 或 `pwj`

左表每条记录需要在右表中匹配一个时间范围，并对窗口内记录做聚合时，应使用 `wj` 或 `pwj`。窗口边界必须与时间列类型匹配，并明确是否包含当前点、是否向前或向后。

### 规则 11：`where` 中存在序列相关条件时必须使用 `and`

逗号连接条件会按顺序逐层过滤；`and` 会在原表上下文分别计算条件后取交集。若条件包含 `deltas`、`ratios`、`ffill`、`move`、`prev`、`cumsum` 等序列相关函数，应使用 `and`，避免过滤顺序改变序列上下文。

### 规则 12：普通过滤条件应优先放置高选择性条件

过滤条件与序列无关时，逗号和 `and` 的结果通常一致。为了减少后续条件处理的数据量，可把日期、代码、分区列等过滤能力强的条件放在前面。

### 规则 13：分布式查询的 `where` 子句不应使用聚合函数

分布式查询需要先通过 `where` 判断相关分区。`sum`、`count` 等聚合函数不应出现在分布式查询的 `where` 子句中，聚合条件应放入分组、`having` 或独立查询阶段。

### 规则 14：分区列过滤必须保持可识别表达式

分布式表查询应尽量使用分区列或系统可识别的分区表达式。不要对分区列使用字符串格式化、任意算术、链式比较，或使用非分区时间列期待分区剪枝。可使用 `sqlDS` 或 `[HINT_EXPLAIN]` 检查扫描分区。

## 三、分组与组内计算规则

### 规则 15：每组一行使用 `group by`

需要把每组压缩成一条结果时使用 `group by`。`group by` 返回结果会自动包含分组列，适合普通聚合、区间统计、分桶统计和二维透视前的预聚合。

### 规则 16：明细等长结果使用 `context by`

需要每一行保留组内计算结果时使用 `context by`。`context by` 不会自动把分组列放入结果，分组列需要在 `select` 中显式选择。

### 规则 17：`context by` 中的执行顺序必须单独检查

`context by ... csort ... limit ... select ... order by` 的顺序是：分组、组内排序、组内限制行数、执行 `select`、最后全局排序。存在 `context by` 时，`limit` 先于 `order by`；不存在 `context by` 时，`limit` 在 `order by` 后执行。

### 规则 18：组内滑窗、前值和差分优先使用 `context by`

每组内部执行 `mwavg`、`tmavg`、`window`、`deltas`、`ratios`、`move`、`cumsum` 等函数时，应在 SQL 中使用 `context by`，必要时配合 `csort`。不要循环每个分组再回表查询。

### 规则 19：累计分组使用 `cgroup by`，并显式排序

需要第一组、前两组、前三组逐步扩大聚合范围时使用 `cgroup by`。`cgroup by` 必须配合 `order by`，且只能使用受支持的聚合函数集合。

### 规则 20：连续区间分组优先使用 `segment`

按连续相同值或连续满足条件的数据段分组时，优先使用 `segment` 生成组标识，再结合 `group by` 或 `context by`。不应在脚本层维护分组编号。

### 规则 21：成交量等累计阈值分段优先检查专用函数或高阶函数

按累计成交量、成交额等阈值切分窗口时，先检查 `volumeBar` 等专用函数；规则较复杂时，可用 `accumulate` 生成分组标识后再聚合。

### 规则 22：数值区间归类优先使用 `asof`

将金额、价格、收益率等数值映射到一组有序区间再统计时，优先使用 `asof(range, value)`。不宜为每个区间单独写 SQL，也不宜循环生成区间标签。

### 规则 23：组内 TopN 聚合优先检查 `aggrTopN`

需要按某个指标选出组内前若干比例或前若干条记录后再聚合时，优先检查 `aggrTopN`。这类任务不应先 `context by having` 过滤，再外层重新 `group by` 聚合。

## 四、结果整形与复合字段规则

### 规则 24：函数返回多列时使用复合字段命名

SQL 中调用返回多个向量或多个结果列的函数时，应使用 `as \`col1\`col2...` 为复合字段命名。典型场景包括回归结果、统计结果和多指标函数。

### 规则 25：同构多档列可转为数组向量

`bid1...bid10`、`ask1...ask10` 等同构多档字段可用 `fixedLengthArrayVector` 合并为数组向量列。分组内多行数据需要收集为数组向量时，可使用 `toArray` 搭配 `group by`。

### 规则 26：长表转宽表和二维透视使用 `pivot by`

需要按两个维度重排数据、行列转换、形成矩阵式结果或透视统计时，优先使用 `pivot by`。透视后可结合 `ffill`、`last`、`avg`、`rowSum` 做后续计算。

### 规则 27：行级多列计算优先使用行函数

宽表或透视结果上需要按行求和、求均值、组合价值等，优先使用 `rowSum` 等行函数。不要为每个类别手工创建列并逐行填值。

### 规则 28：时间频率转换先判断是否需要补空桶

只需要按固定时间粒度聚合时可使用 `bar`；需要补齐缺失时间桶并填充时使用 `interval`；窗口起点需从原始第一条记录开始时，使用 `origin="start"`。

### 规则 29：时间滑动窗口优先使用 tm 系列函数

按时间列滑动计算时优先检查 `tmsum`、`tmavg` 等 `tm` 系列函数。需要把任意函数应用到时间窗口时使用 `twindow`。交易日历窗口可使用 `DURATION` 类型表示，例如 `2XNYS`。

## 五、SQL 元编程规则

### 规则 30：结构化元编程优先于字符串拼接

运行期构造 SQL 时，优先使用 `sql`、`sqlCol`、`sqlColAlias`、`makeCall`、`makeUnifiedCall`、`expr`、`unifiedExpr`、`binaryExpr`。字符串拼接和 `parseExpr` 只适合边界简单、输入可信的表达式。

### 规则 31：宏变量适合动态替换列名

单列动态列名可用 `_$name`，多列动态列名可用 `_$$name`。宏变量适合把外部列名变量嵌入 SQL 元代码，能减少大量 `sqlCol` 组合。

### 规则 32：字段序列适合规则连续列

列名满足“前缀 + 连续数字”时，可使用 `col0...col999` 形式。字段序列可用于查询列、别名、函数参数和数组向量构造。字段数字必须连续，序列长度不超过 32768。

### 规则 33：动态更新和删除使用 `sqlUpdate`、`sqlDelete`

需要动态生成 `update` 或 `delete` 语句时，使用 `sqlUpdate` 和 `sqlDelete`。删除条件中应避免变量名与列名大小写冲突，因为 DolphinDB SQL 列名不区分大小写。

### 规则 34：`parseExpr` 的变量上下文必须显式管理

`parseExpr` 在函数体内不会自动查找函数局部变量；需要解析依赖局部变量的表达式时，应通过字典传入上下文。否则可能出现 `SQL context is not initialized yet.` 等错误。

### 规则 35：批量相似查询可封装为元编程函数

一批结构相同、过滤值不同的查询可封装为生成查询列表的函数，再批量 `eval` 并合并结果。需要集群长期复用时，可注册为 function view。

## 六、执行与性能规则

### 规则 36：分布式表优先直接查询源表

对于分布式表，应尽量把过滤、派生列、分组和聚合保留在同一条 SQL 中。先把分区数据合并为内存表再分组，会失去分布式并行能力并增加中间数据。

### 规则 37：分组结果不跨分区时可使用 `map`

若分区粒度大于分组粒度，并确认每个分组不会跨分区，可在 `group by` 后加 `map`，减少全局二次汇总。使用前必须确认分区方案与分组键关系。

### 规则 38：多表归并应先过滤后合并

多个分布式表参与结果时，应在每个源表内先完成日期、代码、因子等过滤，必要时使用 `in` 下推键集合。结果缩小后再 `unionAll`、`merge` 或矩阵合并。

### 规则 39：复杂 SQL 优化优先检查查询组织

多条 SQL 分步生成中间表、先连接后过滤、分组粒度过细、字符串转换过多、分区列未命中，都是优先审查对象。优化顺序应是减少扫描、合并查询、调整分组粒度、下推过滤，再考虑单个函数替换。

### 规则 40：执行计划和 Trace 用于验证查询行为

`[HINT_EXPLAIN]` 可查看 SQL 执行计划，分布式查询重点观察 `map`、`merge`、扫描分区和行数。SQL Trace 通过 `setTraceMode`、`getTraces`、`viewTraceInfo` 分析复杂 SQL 内部耗时。`setTraceMode(true)` 必须单独执行，不能和待跟踪 SQL 放在同一段脚本中。

### 规则 41：需要保留分组前顺序时使用 `[HINT_KEEPORDER]`

`context by` 可能改变返回顺序。若业务要求结果保持原始顺序，可使用 `[HINT_KEEPORDER]`。

### 规则 42：存储引擎与排序列会影响时间点查询性能

TSDB 引擎支持排序列，对于时间相关、单点查询、每组最新记录等任务可能明显优于 OLAP。性能问题不只来自 SQL 写法，也可能来自存储引擎和排序列设计。
